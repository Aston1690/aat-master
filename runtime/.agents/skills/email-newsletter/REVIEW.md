# Newsletter review

Read before work. Review the entire final issue, not only its first viewport. Record pass, fail, not tested or not applicable with evidence in project notes. Keep concept rendering and email-client compatibility as separate results.

- Review scope matches the request. Screenshots, metadata and exports contain no accidental credentials or private information. Approval and factual verification are recorded separately.
- Delivery class is explicit: visual concept, production email or both. The delivered files match that class.
- Subject, preheader, issue/date, body, CTA, sender/footer and links preserve approved copy. Displayed counts match the actual content.
- No invented company developments, people, metrics or achievements appear. Missing facts use visibly labelled placeholders inside the concept, not invented sample news or a disclaimer only in chat.
- Masthead, type, palette, imagery and logo treatment fit the brand; the full issue has deliberate editorial pacing.
- Desktop and mobile views are readable throughout. No horizontal overflow, clipping, cramped CTA, broken images or tiny footer text remains.
- All final exported PNG/PDF content was inspected; any PDF page breaks were checked. Editable source and needed assets are present.
- Production HTML uses structure and fallbacks appropriate to the targeted email clients; the plain-text version carries the same message and meaningful links.
- Hosted production asset URLs, destination links, sender details, required footer and platform tags are supplied and verified. Placeholder or guessed values block send-ready status.
- Alt text, reading order, contrast, narrow-screen behaviour, dark mode and image blocking were checked in the environments listed in the QA record.
- Email-client claims name the actual clients/testing service used. Untested environments are disclosed. Browser-only preview is never called inbox-tested.
- No agent send, testing-service upload or asset publication occurred. Any human test send is identified with its evidence and approved test recipients.
- A human designer reviews full-length and phone output before external handover; record actual review status.

Wrong copy, invented news, clipped content, missing footer requirements, guessed tags or false compatibility claims prevent a pass for production delivery. A concept may be complete without inbox testing only when its concept status is explicit. Deliverability is not established by visual review.

## Package and handover consistency

- Every requested deliverable and variant is accounted for against the brief, with its assigned copy/source and actual export or route. Reduced scope was explicit; no universal variant count was assumed.

## Team review record

- The job records that the canonical SKILL.md and REVIEW.md were read in full, including version/source revision. Conflicts were raised rather than bypassed.
- No agent edited active skills, checks, tools or model settings. No client identity, palette, contact or personal path was copied into shared instructions or samples.
- Every option has full-size and realistic feed/phone evidence. Missing mandatory inspection is incomplete, not a pass; automated checks never constitute human approval.
- Human review records the reviewer, date, exact artifact revision and outcome for every option. Until this exists, label the handover “awaiting human review”; a person alone performs external release.
- Rejection lessons are recorded for the named owner’s generalised GitHub change within one week. Owner assignment and monthly review status are recorded in the package ownership register, not assumed.
