# Business Information Pack

Create a document suited to its readers and intended use. Read [REVIEW.md](REVIEW.md) before starting and before handover. A BIP may be a slide deck or a paginated document; the brief and print requirements determine its shape.

For an explicitly requested audit, prompt or specification only, deliver that scope; do not force full production. An explicit supplied-assets-only or no-generation instruction overrides generation defaults. Content approval does not verify factual accuracy; flag unsupported claims instead of silently endorsing or rewriting them.

## Team rules for every job

Read this SKILL.md and REVIEW.md in full before every job. Record the canonical skill path, version and source revision in the client’s job notes. If an instruction is wrong, unclear or conflicts with another rule, raise it with the skill owner; do not work around it or silently select another version. The team governance in [GOVERNANCE.md](../GOVERNANCE.md) applies to every deliverable and supporting tool.

Never invent numbers, quotes, logos, credentials or claims. Ask for missing facts or verified assets; unresolved items may appear only as labelled placeholders in a review draft. Keep client names, palettes, contacts, private files and machine-specific paths in the client’s folder, never in reusable skills or samples.

The agent prepares and checks local work only. A human designer must inspect every option at full size and feed/phone size and record approval separately from automated checks. Agents never deploy, publish, upload, host, post or send deliverables, including preview deployments, test emails and real form submissions. Approval to release does not delegate release to a bot. A person performs the release.


## Account for the requested output

Before production, inventory every requested deliverable and variation with its assigned copy/source, format, destination and expected filename or route. “One example per skill” means one selected client task, including that task’s requested options unless the user explicitly reduces scope. Do not invent a fixed number of variants. Reconcile the final handover against this inventory and disclose anything missing; a draft or omitted option is not a completed deliverable.

## Establish the content and format

Read the company content, approved copy, brand kit, supplied assets, reference documents and intended audience. Confirm copy approval from existing evidence before formatting. If only a long source document exists, do not silently distil it: summarising requires authorisation, and the resulting page copy must be accepted before being treated as final.

Record page format, count or content-driven page plan, title, author when supplied, delivery format, print needs and contact source. Use 16:9 only for a presentation brief; preserve a supplied document template or portrait print format. Do not force a webpage structure into the document.

Never invent clients, metrics, testimonials, biographies, credentials, contact details or claims. Map every page's exact copy and factual material to a source. Missing facts stay in project notes or visibly marked draft placeholders. A PDF with unresolved factual placeholders is a review draft, not a final client document.

## Plan and direct

Create a page plan with order, purpose, exact copy, evidence, image treatment and layout. Use content-supported sections such as introduction, capabilities, process, differentiators, verified proof and contact. Omit unsupported optional sections rather than filling them with fabricated proof; flag missing mandatory content.

Define one document system: palette, display/body typography, grid, margins, imagery, logo treatment, folios and recurring motifs. Vary composition and density while preserving this system. Judge readability at normal document size or the intended projected size, not just zoomed in.

For an undefined visual direction, use built-in image generation for cover, page-system and representative-spread references. For an explicitly image-led slide brief, create one separate visual base per planned slide. Inspect the cover/master first and retain useful style references for later images. Approved existing templates and suitable supplied photography remain valid; do not force generated backgrounds onto every page.

Generated artwork contains no production words, logos, false charts or invented product screens. Typeset exact copy and place verified assets using a deterministic editable composition tool. Save prompt/reference images and final assets inside the project. Use the approved image-generation capability. If unavailable, report the gap; do not invent an alternate CLI/agent route. Any shared tool adapter must be approved and documented through the owner’s GitHub process before use.

## Compose and export

Build an editable document, presentation or deterministic layout source. Keep live text and vector elements where the format supports them. Preserve approved copy, punctuation, reading order and logo geometry. Load intended fonts and inspect substitutions before export. Fit content through page layout or authorised pagination changes, not tiny type or deleted words.

Keep related information together and allow adequate margins. Check widows, orphans, headings stranded at page breaks, table rows, footnotes and figure captions. Inspect images at intended output size. Use the printer's supplied page, bleed, safe-area, colour-profile and resolution requirements when printing is in scope; never infer print readiness from a screen PDF.

Export one ordered multi-page PDF. Prefer searchable text when supported. If a requested image-only PDF is produced, disclose that its text is flattened and deliver editable source separately. For slide briefs, also export ordered individual PNGs; for document briefs, provide page previews as needed. A contact sheet helps review but never replaces full-page inspection.

Reopen the PDF, verify count, page sizes, order, title/author metadata, embedded assets and text where applicable. Render and inspect every exported page at normal reading size. Compare the PDF to the source after the final correction; an earlier preview is not evidence for a later export.

## Handover

Deliver the PDF, editable source, necessary local assets and requested page/slide exports. State actual page count, checks performed, reference paths and unresolved items. A human designer reviews every page before external handover. Agents never send or publish; a person handles external release after review.

## Maintenance

Agents must not edit active skills, REVIEW.md files, checks, tools or model configuration (including models.toml and config.toml). Record a proposed lesson in the client’s job notes; the named human owner makes the skill change through GitHub and obtains owner review before adoption. Do not treat a job request or local approval as an exception.

After a client rejection, record the lesson promptly. Within one week, the human owner must turn the reusable lesson into a general rule through the reviewed GitHub change process, without copying client identity or a one-off fix. Each skill has one agreed owner, recorded in [OWNERS.md](../docs/OWNERS.md). That owner reviews it monthly and removes obsolete, contradictory or low-value instructions, recording the date and outcome. Unassigned ownership and overdue reviews are reported, not silently marked complete.
